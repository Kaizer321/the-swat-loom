# The Swat Loom

React + Vite storefront served by the existing Express server. Production orders and inventory are stored in Supabase PostgreSQL. Currency is PKR. Checkout currently supports Cash on Delivery (COD) only.

## 1. Requirements

- Node.js 20 or newer
- A Supabase project
- The Supabase project URL, anon key, and service-role key

## 2. Install dependencies

```bash
npm install
```

The project uses `@supabase/supabase-js` on the server. Do not use `npm ci` until the lockfile has been regenerated by `npm install`.

## 3. Create the database

1. Open your Supabase project.
2. Go to **SQL Editor** → **New query**.
3. Paste and run all of `supabase/schema.sql`.
4. In Supabase **Project Settings → API**, copy the Project URL, anon/public key, and service_role key.

The SQL creates products, customers, orders, payments, and admin_users. RLS is enabled and direct browser access is revoked. The Express server accesses the database with the server-only service-role key.

## 4. Configure environment variables

Copy `.env.example` to `.env.local` and fill in:

```env
GEMINI_API_KEY=your_gemini_key
SUPABASE_URL=https://YOUR_PROJECT.supabase.co
SUPABASE_ANON_KEY=your_supabase_anon_key
SUPABASE_SERVICE_ROLE_KEY=your_supabase_service_role_key
```

**Never** prefix the service-role key with `VITE_`, commit `.env.local`, paste it into chat, or expose it in frontend code. Keep `.env.local` out of Git.

## 5. Create the separate administrator login

1. In Supabase, open **Authentication → Users → Add user**.
2. Create the admin with an email and a strong unique password. Confirm the user if your project requires confirmation.
3. Copy that user's UUID.
4. In SQL Editor, run this query, replacing the values:

```sql
insert into public.admin_users (user_id, email)
values ('PASTE-AUTH-USER-UUID-HERE', 'admin@example.com');
```

Only users listed in `admin_users` can access admin APIs. Do not create public admin sign-up. Remove the old hardcoded `SWAT123` password; it is no longer used.

## 6. Run locally

```bash
npm install
npm run dev
```

Open the URL printed by Vite/Express, normally `http://localhost:3000`. Keep the terminal open. The server listens on `0.0.0.0` for hosting, but browsers should use `localhost` locally.

The first successful `GET /api/products` seeds Supabase with the existing catalogue from `constants.ts` and `SIGNATURE_SHAWLS` if the products table is empty. Review every seeded product price in the admin dashboard before launch: the app now labels prices as PKR, but it does not convert old numeric prices automatically. Existing browser localStorage product edits and orders are not migrated automatically; local/demo orders should not be treated as real customer orders.

## 7. Verify the integration

- Visit `http://localhost:3000/api/health`; check `databaseConfigured: true`.
- Visit `http://localhost:3000/api/products`; it should return the catalogue as JSON.
- Place a test COD order with a test customer and verify it appears in Supabase `orders`, `order_items` are stored in the `items` JSONB column, and a `payments` row is created.
- Open the admin dashboard from the existing hidden footer trigger and sign in with the allow-listed admin email/password.
- Change the order status and verify the `orders.status` value changes.
- Track the order using its order ID or tracking code.

## 8. Order/payment behavior in this phase

- The server recalculates the price from current database product prices. It does not trust cart-submitted prices.
- Checkout creates an order with `status = Pending`, `payment_method = COD`, and `payment_status = Pending`.
- COD is not marked paid until the business confirms collection. Online payment providers are intentionally not wired in this phase.
- Tracking lookup requires the order ID or tracking code. For a public production store, consider adding a second verification factor (such as phone number or email OTP) before exposing customer address/contact details through tracking.

## 9. Deployment note

This app requires a persistent Node.js server because `server.ts` hosts the API, Vite middleware in development, and static assets in production. Deploy the Express app to a Node host (for example Render or Railway) and set all environment variables there. A static-only Vercel deployment will not run this Express server as-is. Keep the Supabase service-role key in the backend host's secret environment variables only.

## 10. Current limitations / next phase

- No online payments yet (COD only, as requested).
- Product images uploaded in the current admin UI are browser data URLs; move image uploads to Supabase Storage before using this admin upload workflow in production.
- Add rate limiting, order lookup verification, stock reservation/transaction handling, email/SMS notifications, and audit logs before a high-volume launch.

## Security and production notes (November 2026)

- The server now rate-limits admin login, checkout, public order tracking, Gemini endpoints, and the Live WebSocket per server process. If you deploy multiple server instances, configure a shared Redis/Upstash rate-limit store before launch.
- Public order tracking now requires both the order/tracking number and the checkout phone number. It no longer returns customer name or contact/address fields. Admin product image uploads now go to the `product-images` Supabase Storage bucket rather than persisting data URLs in product rows; the migration creates/configures this public-read bucket.
- COD order and payment creation now uses the `create_cod_order_atomic` PostgreSQL function. Run `supabase/migrations/20261113_atomic_cod_order.sql` in Supabase SQL Editor before deploying this server version.
- In production, cross-origin browser requests are disabled unless `CORS_ORIGIN` is explicitly configured. Same-origin frontend/API requests continue to work.
- Production server command is `npm start` (`tsx server.ts`); Node.js 20+ is recommended.

Stock quantities are now editable in the admin product form and decremented atomically during COD checkout. A stock value of 0 intentionally means unlimited/not tracked, preserving the existing catalogue until you enter real stock quantities. Still required before a high-volume launch: replace per-process rate limits with a shared store when horizontally scaling. Configure `CORS_ORIGIN` only if the frontend and API are on separate trusted origins.

## Order confirmation emails (Resend)

The server sends a confirmation email after a COD order has been saved. Email delivery is best-effort: a Resend error is logged but does not cancel or roll back the order.

For local testing, add these server-side variables to your existing `.env` (do not replace your existing Supabase or Gemini variables):

```env
RESEND_API_KEY=re_your_resend_api_key
EMAIL_FROM=The Swat Loom <onboarding@resend.dev>
EMAIL_TEST_MODE=true
EMAIL_TEST_TO=the-email-address-registered-with-Resend@example.com
PUBLIC_SITE_URL=http://localhost:5173
```

With `EMAIL_TEST_MODE=true`, every checkout confirmation is sent only to `EMAIL_TEST_TO`, because Resend's onboarding sender is restricted to the account's verified recipient. After verifying a sending domain in Resend, set `EMAIL_FROM` to an address on that domain and change `EMAIL_TEST_MODE=false` so customers receive their own confirmations. Never prefix the API key with `VITE_` or expose it in frontend code. `.env.example` contains placeholders only.

The cart now has decrement/increment controls. Quantities are capped at 20 and at the product's available stock when stock is greater than zero. The Admin Dashboard Orders tab includes a search for customer name, email, phone, city, order ID, tracking code, and product name; the existing status filters still apply.
